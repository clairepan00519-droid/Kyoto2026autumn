## v63（修正「Invalid Refresh Token: Already Used」上傳失敗）

**問題**：上傳圖片（例如紅葉前線地圖）時，有機率跳出英文技術錯誤「Invalid Refresh Token: Already Used」，上傳失敗。

**原因**：Supabase 的登入換新（refresh token）只能用一次。當背景同步、輪詢和「上傳照片」這類操作幾乎同時發生，都想換新登入時，只有第一個換得到，其餘的會被 Supabase 拒絕，並回傳這則英文訊息。網站原本已經有基本防護，但沒有涵蓋所有情況。

**這次修正**：
1. 換新登入前，一律先看本機硬碟（localStorage）目前的內容，若已經有別的分頁／背景任務剛換好的新登入，直接沿用，不再重複換新。
2. 真的撞見「已被用掉」時，不會立刻放棄，會再等一下、重新確認一次，讓其他並行的換新有機會先完成。
3. 只有真的沒有辦法時才提示使用者，而且改成親切的中文說明＋「要現在重新整理嗎？」的按鈕，不再是原始英文技術訊息。這台裝置上的資料都已經存好，重新整理不會遺失內容，只需要重新做一次剛剛沒完成的那個操作（例如再上傳一次圖片）。

已用多組情境測試（本機已有更新的登入／真的過期／三個同時發生的請求／錯誤提示的呈現方式）驗證修正正確。

## v63（修正上傳照片時的「Invalid Refresh Token」錯誤）

**問題原因：** Supabase 的登入權杖（refresh token）用過一次就會失效換新。上傳照片時，程式常常會同時送出好幾個網路請求（上傳本身＋背景同步／輪詢）。如果權杖快過期，這些請求會「同時」各自想換一個新的，只有最快的那個換得到，其餘的會被 Supabase 拒絕，回報「Invalid Refresh Token: Already Used」，並直接把這段英文錯誤訊息顯示給你看。

**修正方式：** 現在所有同時發生的請求會共用同一次換新，不會再互搶；真的搶輸時也會先確認是不是已經換好了，是的話就直接沿用，不會顯示錯誤。已用模擬情境測試過：5 個同時發生的請求，只會真正跟 Supabase 要 1 次新權杖。萬一真的遇到登入過期（例如很久沒開網站），會改顯示「登入資訊過期，請重新整理頁面」，不會再顯示英文原始錯誤。

## v46 修正「同步後資料消失」與「家人看到的跟我不一樣」

**如果你已經在用舊版，請先做這一步：** 到 Supabase SQL Editor 重新貼上並執行一次新的 `SUPABASE_SETUP.sql`（可重複執行，不會刪資料），這會加上一個資料庫觸發器，讓 `updated_at` 一律由資料庫時間決定。

修正了兩個造成資料消失／版本不一致的問題：

1. **同步時間比較改用資料庫時間，不再用手機自己的時鐘。** 舊版由每台裝置自己蓋時間戳，只要有一支手機的系統時間不準（快、慢或時區設錯），比較新的資料就可能被誤判成比較舊而被覆蓋掉，或是這台裝置不再接受家人之後的更新，看起來像「卡住」在自己的版本。
2. **同步時改用合併而非整包覆蓋。** 舊版是「筆記」「自訂景點」「排序」等每一類資料一次整包互相蓋過去，如果你和家人在幾秒鐘內剛好都改了同一類裡的不同項目，其中一邊會被整包蓋掉、看起來資料消失了。新版推送前會先讀一次雲端最新內容，跟本機要送出的內容合併（聯集）後再送出，兩邊的變更都會保留。
3. **離線快取改成「先連網、連不到才用快取」。** 舊版手機／電腦會優先顯示上次快取的網站版本，即使你已經更新部署，家人裝置也常要重新整理兩次才會換到新版，這也是造成「看到的跟我不一樣」的常見原因。

⚠️ 這個合併機制目前是「聯集」而非真正的欄位級版本控制，所以理論上還是有一種情況會讓「明確的刪除」被合併回來（例如你剛好在別人離線很久之後、才刪除同一筆資料）。日常同時編輯（不同景點、不同筆記、不同照片）都不會再有資料消失的問題；如果要刪除某個項目，建議先確認家人裝置都已連網同步過一次再刪，最保險。
